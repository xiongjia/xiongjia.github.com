# part-0003 三代交付史与 AI→Software→Result 的失败

- **输入来源**: 本地 pdf 预提取文本（source-03.txt，arXiv:2606.05608v1 [cs.SE]）
- **原文链接**: <https://arxiv.org/html/2606.05608v1>

## 摘要

**§3.1 三代软件交付（Table 1）**——商业软件史可理解为「复杂度不断移离终端用户」：

| 世代                  | 核心机制                               | 复杂度承担者             | 收入模型                | 代表              |
| --------------------- | -------------------------------------- | ------------------------ | ----------------------- | ----------------- |
| Software 1.0（Local） | 代码 + 数据本地执行                    | 终端用户（安装、维护）   | License 售卖            | Microsoft、Oracle |
| Software 2.0（SaaS）  | 代码 + 数据云端执行                    | Vendor（基础设施、更新） | 订阅                    | Salesforce、AWS   |
| Software 3.0（AaaS）  | Agent 云端自主运行（理解、构建、运行） | Agent                    | 按结果（outcome-based） | OpenAI、Anthropic |

作者点出的规律：每次转移都是「最有能力吸收复杂度的一方吸收它，最不擅长管理的一方被
解放」。SaaS 把企业从机房解放出来；AaaS 承诺把企业从「必须说明结果该如何产生」中解放
出来——用户只需说明**想要什么结果**。

**§3.2 "AI →Software →Result" 为何走不通**：迄今主流的 enterprise AI 范式是
AI-augmented development——用 LLM 帮人类工程师更快写代码，仍停留在传统软件生命周期内。
作者把这个管线记为 "AI →Software →Result"，并指出三个结构性弱点：

1. **Bottleneck persistence（瓶颈仍在）**：人仍是设计决策、架构、集成测试、部署的
   critical path；AI 只加速了实现（implementation）这个子步骤，没有把人从任何阶段移除
1. **Complexity ceiling intact（复杂度天花板原封未动）**：最终交付物仍是传统软件系统
   S = (C, D, E)，复杂度仍随 |D| 缩放，任何修改仍需人的理解——AI 只是让 D 的构建稍快
1. **Iteration latency（迭代延迟）**：即便有 AI 协助，任何功能变更仍要走完
   需求 → 设计 → 代码 → 测试 → 部署 全链；延迟下限仍受制于人际沟通与协调速度

## 要点归纳

- 分析变量是「complexity owner」：三代史 = 复杂度所有权从 end-user 到 vendor 再到
  agent 的迁移；收入模型（license → subscription → outcome-based）与承担者同步变化
- "AI →Software →Result" 被判失败的原因不是 AI 不够强，而是它仍被架在传统范式的
  生命周期里（人在关键路径、制品仍是静态软件、延迟不变）
- AaaS 因此被定位为三代谱系的「逻辑终点」而非又一种商业模式变体

## 术语 / 概念

- **complexity owner（复杂度承担者）** — 论文三代史分析的核心变量：谁承担
  安装 / 维护 / 理解 / 构建 / 运行等复杂度
- **license / subscription / outcome-based（授权售卖 / 订阅 / 按结果计费）** — 三代
  对应的收入模型
- **AI-augmented development（AI 辅助开发）** — "AI →Software →Result" 管线；论文判其
  为「范式内的局部优化」反面教材
- **bottleneck persistence / iteration latency（瓶颈持续 / 迭代延迟）** — 该管线的两个
  结构性弱点

## 原句摘录

> Each transition follows the same pattern: the party best positioned to absorb complexity
> absorbs it, and the party least positioned to manage it is liberated from it. SaaS
> liberated businesses from server rooms; AaaS promises to liberate them from the need to
> specify how a result should be produced—they need only specify what result they want.
