# supabase-storage-client

TypeScript prototype demonstrating **basic Supabase Storage** usage from
Node.js against a **local** Supabase instance, using the official
[`@supabase/supabase-js`](https://www.npmjs.com/package/@supabase/supabase-js)
SDK. Package manager: **pnpm**. Modeled after the [`ali-oss-client`](../ali-oss-client/)
prototype.

Status: `experimental` (local project config included; end-to-end run pending)

## Features

- Configuration via environment variables, with sensible local defaults (no
  `.env` needed for a plain local test)
- Anon key auto-discovery from the running local project
  (`supabase status -o env`) when `SUPABASE_ANON_KEY` is not set
- List buckets
- Create bucket (private) if it does not exist yet
- List objects under a demo prefix
- Upload object (`upsert: true`, so re-runs overwrite instead of failing)
- Download object
- Generate signed URL for GET (time-limited download access)
- Generate signed URL for PUT upload (credential-free, server-side expiry)
- Public URL (getPublicUrl — shown for completeness; 404s while the demo
  bucket stays private)
- Delete object + delete demo bucket (cleanup: demo object always removed;
  bucket deleted only when this run created it — pre-existing buckets are
  left in place)

## Local Supabase Setup

### 1. Install the Supabase CLI

```bash
brew install supabase/tap/supabase   # macOS
# or: https://supabase.com/docs/guides/cli/getting-started
# update an existing install with: supabase update
```

The local Storage API / Storage images come from the CLI version, so update
the CLI before testing if yours is old (`supabase --version`).

This prototype ships its own Supabase project config under `supabase/`
(generated by `supabase init`, storage enabled in `supabase/config.toml`),
so you can start the local stack straight from this directory:

### 2. Start the local stack

```bash
supabase start   # Docker required; first run pulls the images
```

`supabase start` spins up the full local stack (Postgres, PostgREST, Storage
API, Auth, …) with the REST API at `http://127.0.0.1:54321`. Storage is
enabled by default (`[storage] enabled = true` in `supabase/config.toml`).

To stop it again: `supabase stop` (add `--no-backup` to also drop the data).

## Configure / Usage

```bash
pnpm install   # install dependencies (in this directory)
pnpm dev       # run the demo against the local Supabase
```

- **`pnpm dev`** runs the source directly (`tsx src/index.ts`) — edits take
  effect on the next run without building.
- `pnpm demo` runs the compiled `dist/index.js` — re-run `pnpm build` first.

No `.env` file is required for a local run: the URL defaults to
`http://127.0.0.1:54321` and the anon key is auto-read from the running
local project. If the CLI lookup fails (e.g. supabase not running, or the
binary not on `PATH`), the demo prints the setup instructions instead
(dry-run).

Override via `.env.dev.local` (copied from `.env.example`) when needed:

```bash
# .env.dev.local
SUPABASE_URL=http://127.0.0.1:54321
# SUPABASE_ANON_KEY=eyJ...        # auto-read from `supabase status` if unset
SUPABASE_BUCKET=supabase-storage-demo
# SUPABASE_DEMO_PREFIX=demo/supabase-storage-client/
# SUPABASE_KEEP_DEMO_OBJECT=true  # skip automatic cleanup
```

The demo loads `.env.dev.local` first, falling back to `.env`
(`dotenv.config({ path: [".env.dev.local", ".env"] })`). `.env`,
`.env.local` and `.env.*.local` are gitignored — only `.env.example` is
committed.

With a running local stack, `pnpm dev` walks through: list buckets → ensure
bucket → list objects → upload → download → signed URL (GET) → signed URL
(PUT upload) → public URL → cleanup (the demo object is removed afterwards;
if this run created the bucket it is deleted too — set
`SUPABASE_KEEP_DEMO_OBJECT=true` to keep the object and bucket).

## Testing a signed upload URL with curl

The demo prints a signed **PUT** upload URL for the demo object. Uploading
with curl works because a signed upload URL is credential-free — no headers
beyond the body are required:

```bash
# 1. run the demo and keep the demo object
SUPABASE_KEEP_DEMO_OBJECT=true pnpm dev

# 2. while the URL is valid (its lifetime is set server-side, not by the
#    client), PUT content to the URL printed under "Signed upload URL
#    (PUT, ...)"
curl -X PUT \
  -H "Content-Type: text/plain" \
  --data-binary "hello from curl" \
  "<signed upload URL>"

# 3. verify with the signed GET URL printed by the demo
curl "<signed download URL>"
```

`--data-binary` is used instead of `--data` so curl does not strip trailing
newlines. Unlike the download URL (60 s), the signed upload URL has **no
client-side expiry** — the token's lifetime is set server-side, and the
default varies by Storage API version (the current TS Storage API uses 60 s;
older Go versions used hours). The demo generates it with `{ upsert: true }`,
so the curl PUT overwrites the existing demo object and re-running the demo
overwrites it again — the test is repeatable.

One timing caveat: the signed **download** URL printed by the demo expires
60 s after it is generated. Run steps 2–3 promptly; if it has expired by the
time you verify, re-run the demo (or call `createSignedUrl` again) to print a
fresh one.

## Debugging with VS Code

The repo-root `.vscode/launch.json` carries a configuration for this
prototype (**Debug supabase-storage-client (tsx)**) on this machine — but
that file is **gitignored** (the global `~/.gitignore_global` ignores
`.vscode/`), so it is not committed. On a fresh clone, create or extend
`.vscode/launch.json` with:

```jsonc
{
  "name": "Debug supabase-storage-client (tsx)",
  "type": "node",
  "request": "launch",
  "cwd": "${workspaceFolder}/prototypes/supabase-storage-client",
  "program": "${workspaceFolder}/prototypes/supabase-storage-client/src/index.ts",
  "runtimeExecutable": "${workspaceFolder}/prototypes/supabase-storage-client/node_modules/.bin/tsx",
  "console": "integratedTerminal",
  "internalConsoleOptions": "neverOpen",
  "sourceMaps": true,
  "skipFiles": [
    "<node_internals>/**",
    "${workspaceFolder}/prototypes/supabase-storage-client/node_modules/**",
  ],
}
```

This is tsx's officially documented debug setup
(<https://tsx.hirok.io/vscode>): the `tsx` CLI is the debugged executable
instead of `node --import tsx`, so breakpoints reliably map back to the
`.ts` sources. Then:

1. Make sure dependencies are installed: `pnpm install`.
1. Make sure the local stack is running: `supabase start` (from this
   directory).
1. Open the **repo root** in VS Code, go to the **Run and Debug** panel,
   select **Debug supabase-storage-client (tsx)**, and press F5.

Every F5 launches a fresh process that reads the current `.ts` files, so
breakpoints always hit your latest edits. `cwd` is the prototype directory,
so dotenv and the `supabase` CLI lookup both resolve correctly. To override
environment variables without touching `.env.dev.local`/`.env`, add an `env`
block to the configuration (e.g. `"env": { "SUPABASE_BUCKET": "my-bucket" }`).

## Notes

- SDK docs: <https://supabase.com/docs/reference/javascript/storage-createbucket>
- **Local anon key**: the key changes per project, but it is public by design
  (it goes into every browser client). Reading it from `supabase status -o env` keeps the prototype zero-config; `supabase status` (table view) shows
  it too. For a remote project set `SUPABASE_URL` + `SUPABASE_ANON_KEY`
  explicitly.
- **Storage is open to the anon key by default** — in a default project the
  public `anon` key can create buckets, upload, and delete objects (the demo
  relies on this). In production, enable RLS policies on
  `storage.objects`/`storage.buckets` before shipping; `service_role` keys
  bypass RLS entirely and must never reach the browser.
- **`getPublicUrl` is synchronous** (no network call) — it only stamps the
  URL scheme, it does not prove the object exists. Private buckets 404 those
  URLs; use signed URLs instead.
- **Deleting a non-empty bucket fails** — the demo removes the demo object
  before deleting the bucket, and only deletes buckets it created itself
  (a pre-existing `SUPABASE_BUCKET` is never deleted — the demo touches only
  keys under the demo prefix inside it). Both cleanups are best-effort (the
  object cleanup failing makes the bucket deletion fail too, but that is
  reported, not fatal). A bucket left behind by a `SUPABASE_KEEP_DEMO_OBJECT`
  run is not auto-removed by later runs — delete it manually if you want it
  gone.
- **Not part of GitHub CI**: this prototype is not built or tested by the
  repo's GitHub Actions workflow (CI only covers the main MkDocs site and
  Python toolchain). Verify it locally with `pnpm typecheck` / `pnpm build`
  (see [AGENTS.md](../../AGENTS.md) → Prototype Convention).
