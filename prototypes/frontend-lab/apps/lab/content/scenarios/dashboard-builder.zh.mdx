## 场景

B15 提出两个看似相关、其实独立的问题：

- **布局**——一格格卡片能否仅靠指针 _和_ 键盘就完成排序与调宽，刷新后是否还在？
- **图表**——每个图表库到底花多少字节、多少毫秒，这些成本换回了什么？

示例（`demos/scenarios/dashboard-builder`）用与看板相同的 store + 持久化契约回答第一个问题，并把
同一份确定性数据交给三种渲染器、逐个测量挂载成本来回答第二个。第四张卡是资金流向 Sankey——上述三个
渲染器都不自带，正是「布局本身就是工作量」的例子。

## 布局契约

| 关注点 | 归属                              | 存成什么                       |
| ------ | --------------------------------- | ------------------------------ |
| 顺序   | store 里的卡片数组                | 卡片的 JSON 数组               |
| 宽度   | 每张卡的 `span: 1 \| 2 \| 3`      | 卡片的一部分                   |
| 渲染器 | 每张图表卡各自选择                | 卡片的一部分                   |
| 编辑态 | 组件本地状态                      | 不持久化（属于本次会话的选择） |
| 动画   | Motion `layout`，仅在非编辑态启用 | —                              |

拖拽把手、宽度按钮和渲染器下拉只在编辑态存在。这不是简化：只读的仪表盘不该被误操作弄乱；而键盘
路径（聚焦把手、`Space`、方向键、`Space`）也只有在「布局」这件事上才有意义。

## 对比

数据：由一个带种子的 LCG 生成的 12 周序列，三种渲染器完全一致。加载成本取构建产物分块的 gzip 大小
（`pnpm bundle:report`）；渲染成本是「首次渲染到 DOM 提交」，由示例自带的 `useMountCost` 在重新
挂载后测量（点「Measure again」），此时分块已预热。

| 渲染器   | 输出   | 额外加载（gzip）                | 渲染（12 个点）                        | 是否跟随 token                         |
| -------- | ------ | ------------------------------- | -------------------------------------- | -------------------------------------- |
| 手写 SVG | SVG    | 0 kB（算在示例分块里，约 6 kB） | 0.7–0.9 ms                             | 是，`var(--primary)`                   |
| Recharts | SVG    | **102.8 kB**（原始 358.2 kB）   | 2.6–3.0 ms                             | 是，`var(--primary)`                   |
| Chart.js | canvas | **56.3 kB**（原始 162.2 kB）    | 预热后 0.7–0.9 ms；首次冷挂载约 293 ms | 否——token 要靠 `getComputedStyle` 解析 |

作为参照：整个实验室的 JavaScript 把所有懒加载分块都算上约 730 kB gzip，两个图表渲染器是其中最大的
两笔单项增量。

### 这些数字说明什么

- **小图表上，加载成本占绝对主导。** 12 个点在三种渲染器下都不到 3 ms；103 kB 与 0 kB 的差距，比
  0.8 ms 与 3 ms 的差距大了两个数量级。只放一条迷你折线的面板，不该引入图表库。
- **Recharts 不是渲染慢，是运载贵。** 那 103 kB 买的是刻度、坐标轴、tooltip、自适应容器，以及外面
  那层 React 元素——这些原本要你自己写。
- **Chart.js 渲染看起来最便宜，集成最贵。** 手动注册、canvas 取色，以及「切换主题不会自动重绘」。
  在这个环境里它的冷启动首挂载约 293 ms——一次性的开销，热挂载会把它藏起来，这正是示例提供
  「Measure again」而不是相信第一次数字的原因。
- **手写 SVG 便宜，是因为功能清单是空的。** 坐标轴、刻度、tooltip、图例、框选、日期刻度都还没写；
  那部分工作量才是 0 kB 方案的真实价格。

### 分叉的场景：资金流向 Sankey

第四张图表卡是一张 Sankey——收入 → 各类支出/储蓄 → 具体账户——它正是「库总比自己写便宜」的反例。
Recharts 没有 Sankey，Chart.js 需要社区插件，而你会想到安装的 `d3-sankey` 其实是布局库而不是渲染器。
所以布局放在 `packages/charts/src/sankey-layout.ts`：一个纯函数，负责节点取值、统一的纵向比例尺和
缎带锚点切片；`sankey.tsx` 只把结果变成路径和标签，另有 9 个 `node:test` 用例钉住几何。

三个让它「像流量」而不是「一堆等宽箭头」的决定：

- **跨层共用一把比例尺**：¥8k 流进某个桶，流出时厚度不变。
- **锚点是节点上的切片，不是整个节点**：节点按目标顺序分发自己的带宽，于是 ¥12k 与 ¥2k 两条缎带是
  切分节点，而不是互相重叠。
- **中间节点取 `max(流入, 流出)`**：有损耗（四舍五入、未列出的流向）的节点仍保留流出的厚度。

颜色来自新增的 `--chart-1..5` 分类 token（浅色/深色各一套），因此这张图能跟随明暗与样式预设，而不必
写死十六进制色值。Sankey 卡刻意没有渲染器切换：它是另一种图表类型，不是同一张图的另一种实现。

## 方法

- 一个渲染器一个分块：`@frontend-lab/charts/recharts` 与 `@frontend-lab/charts/chartjs` 是独立入口，
  通过 `lazy()` 加载。选择哪个就下载哪个，默认面板两笔都不付。
- 渲染成本由每个渲染器内部调用同一个 hook 测得，所以数字可比。页面首次挂载的那次测量被刻意排除：
  它同时支付了整页布局的成本，不属于图表。
- bundle 报告读取 `apps/lab/dist` 并对每个产物 gzip；预算写在
  `apps/lab/plugins/bundle-report.ts`，超出即命令失败。

## 坑

- **动态拼出来的 Tailwind 类名并不存在。** `col-span-${span}` 生成不出任何 CSS；宽度到类名的映射必须
  写死，扫描器才看得见。
- **Motion 的 `layout` 与 dnd-kit 都要写 `transform`。** `layout={!editing}` 就是全部修复；拖拽期间
  做布局动画只会抖，不会顺。
- **Chart.js 的注册是静默的。** 忘了 `CategoryScale`，图画出来没有坐标轴，也不会报错。
- **canvas 读不到 CSS 变量。** `--primary` 必须在渲染时解析成具体颜色，切换主题还要等一次重渲染。
- **Recharts 需要父级有尺寸。** `ResponsiveContainer` 放在没有高度的 flex 子项里，高度就是 0。

## 没做的

- **不做取数、筛选、时间范围。** 数据集是常量，比较才稳定。
- **不做拖拽调宽。** 网格卡片的指针缩放需要像素级数学，会淹没图表对比；宽度用按钮，且保持键盘可达。
- **不再引入第二个布局动画库。** Motion 在 B12 已经证明过这一层；这里真正有意思的冲突是
  `layout` 与 `drag`，不是库与库。
