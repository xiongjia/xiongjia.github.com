## 场景

B14 把三项各自验证过的技术组合起来：跨容器拖拽（B12 的 dnd-kit 层）、每实例状态（B11 的 store
工厂）、进出场动画（B12 的 Motion 层）。问题恰恰出在组合处：这三者都乐於把同一个 `transform` 或
同一个 `localStorage` 键当成自己的地盘。

交付物是一个看板，它有三条可独立验证的性质：

1. **拖拽** 能把卡片移到别的列，也能在列内重排，且视觉状态全程跟着指针。
2. **持久化** 能活过刷新——并且损坏的存档会回落到默认值，而不是让首屏崩掉。
3. **键盘** 能做到指针能做的一切：用把手重排，用卡片上的按钮换列。

## 模型

```text
cards      Record<cardId, { id, title, tag }>
columns    Record<'backlog' | 'doing' | 'done', cardId[]>
```

卡片属于哪一列是**推导**出来的，没有可以和列表跑偏的 `card.column` 字段。所有变更都经过一个函数：

```ts
moveCard(board, cardId, toColumn, toIndex)
```

跨列拖拽是一串 `moveCard`：`onDragOver` 把卡片移进悬停的列，`onDragEnd` 做最终重排。这个拆分是
「拖动时就能看到卡片落进新列」的唯一原因。

## 各层的边界

| 层    | 负责                           | 不负责           |
| ----- | ------------------------------ | ---------------- |
| 模型  | 哪张卡在哪一列的哪个位置       | 渲染、时序、存储 |
| 拖拽  | 传感器、碰撞、浮层             | 看板本身         |
| Store | 看板实例 + 稳定的 actions      | 持久化           |
| 示例  | 防抖写入、校验、播报、键盘扩展 | 重排算法         |

把持久化放在 store 之外，是对 `zustand/persist` 的刻意偏离：一次拖拽每个 `onDragOver` 都会产生一次
更新，朴素接法就是每次更新都写一遍 `localStorage`。现在的做法是订阅 + 200ms 防抖、卸载时立即 flush、
读取时校验结构。

## 检查项

- 拖拽：从 Backlog 拖到 Done，卡片留在 Done，两侧计数一致。
- 持久化：刷新后存下的看板渲染出同样的卡片与列，存下的 JSON 也能解析回合法看板。
- 键盘：`Space` + `ArrowDown` + `Space` 通过排序把手在列内重排；← / → 按钮只靠焦点即可换列。
- 动画：删除的卡片通过 `AnimatePresence` 淡出；可排序卡片永远不要求动画 `transform`，因为拖动期间
  那是 dnd-kit 的属性。

## 从 B12 继承的坑

- `layout` 与 `drag` 都会写 `transform`。看板只动画透明度，不动 layout。
- `DragOverlay` 渲染被举起的那份副本，列表里的卡片因此可以留在原地、保持布局。
- `activationConstraint: { distance: 4 }` 是「点卡片上的按钮仍然是点击」的前提。

## 这里不做的

- **不做泳道、筛选或 WIP 上限。** 每一项都是产品决策，只会把这一批要证明的三条性质淹掉。
- **不做服务端同步。** 持久化是本地存储契约；远端看板需要冲突解决，那是另一个实验。
- **不做看板之间的拖拽。** 跨容器排序才是难点；跨 _store_ 排序需要一个共同父级 store，而那正是
  「每实例工厂」刻意禁止的东西。
