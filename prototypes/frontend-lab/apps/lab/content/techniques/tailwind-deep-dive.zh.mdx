## 这一批解决什么

实验室里 Tailwind v4 早就在用了，所以 B8 不是入门，而是组件库必须吃透的一批特性：每个特性
配一个能跑的示例，外加一句能带走的结论。

| 实验                | 它回答的问题                                     |
| ------------------- | ------------------------------------------------ |
| 容器查询            | 这个组件该响应窗口宽度，还是响应自己的宽度？     |
| `has-*` / `peer-*`  | 有多少交互状态本该由 CSS 承担，而不是 React？    |
| 变体规则            | 一个变体到底编译成了什么选择器？                 |
| Keyframes 与 Motion | CSS 动画什么时候够用，什么时候中断体验才是关键？ |
| Grid 与 subgrid     | 行与行怎么对齐？怎么不再写死列数？               |

## 心智模型

Tailwind v4 只会把它在源码里见到的工具类编译成一份 CSS，而**变体就是选择器模板**：`sm:` 是
媒体查询，`@sm:` 是容器查询，`has-[…]:` 就是 `:has(…)`，`data-[…]:` 是属性选择器，`*:` 是
`& > *`。几乎所有「Tailwind 里怎么实现 X」的问题，实际都是「我需要哪个选择器」，答案往往是
浏览器原生能力，工具类只是给它起了名字。

由此有三条推论：

- **组件默认用容器查询，页面才用视口查询。** 窗口变了但卡片所在的列没变，卡片却重排了，这是
  缺陷不是特性。
- **原生状态优先于复制状态。** `:invalid`、`:checked`、`open`、`aria-sort` 本来就在 DOM 上，
  `has-*` / `peer-*` / 状态变体直接读它们；React state 只留给 DOM 里不存在的数据。
- **目标不是提升选择器权重，而是对齐 DOM 的唯一事实来源。** `has-[input:invalid]` 不会像
  `useState` 那样与真实校验结果脱节。

## 这些实验改动了什么

- 新增 `styles/animations.css` 并在 `@theme` 里注册 `--animate-kick`：示例目录只能放
  `demo.tsx` 和说明（检查会拦），所以带名字的关键帧动画注册在共享样式表里。
- `@container` 是 B10 可拖拽面板的基础：面板就是容器。
- 变体实验里的 `data-state` 契约，B11 和 B12 会继续用：当状态由 store 而不是本地 `useState`
  持有时，这套 CSS 不需要改。

## 边界

- 每个实验都用 DOM 验证：计算样式、`getAnimations()`、`matches()`。截图证明不了一个 hover 状态
  背后的选择器。
- Tailwind v4 的变体表还在演进（`nth-*`、`in-*`、`not-*` 都是在小版本里补齐的）。示例只用固定
  版本里确实存在的变体，写错时不会「降级」——而是根本不生成 CSS。
