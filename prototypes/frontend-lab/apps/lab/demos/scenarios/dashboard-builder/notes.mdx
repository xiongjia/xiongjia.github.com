## What this proves

A dashboard is two independent problems stacked:

1. **Layout** — cards you can reorder and resize, persisted, usable with a pointer and with a
   keyboard.
2. **Charts** — the same data drawn by renderers with very different cost profiles, where the
   choice is a budget question, not a taste question.

This demo keeps them independent: the layout store knows nothing about charts, and each chart card
can switch renderer without moving.

## The layout

- Cards live in the store (`createStoreContext`), so order, span and renderer persist together.
- `rectSortingStrategy` is the grid counterpart of the kanban's vertical strategy; dnd-kit computes
  the reorder from rectangles, so a 1-column and a 3-column card can swap places.
- Editing is a mode: drag handles, width buttons and the renderer select only exist while it is on.
  A dashboard you read is not a dashboard you can break by accident.
- `motion.div layout` is enabled **only when editing is off** — while editing, dnd-kit owns
  `transform`, and two owners of the same property produce jitter. Leaving edit mode animates the
  layout back into place.
- Keyboard: focus a ⠿ handle, `Space` to pick up, arrows to move, `Space` to drop. Width buttons are
  ordinary toggle buttons with `aria-pressed`.

## Three renderers, one dataset

| Renderer   | Model                        | Output | Colours                          |
| ---------- | ---------------------------- | ------ | -------------------------------- |
| `svg`      | hand-written, no deps        | SVG    | `var(--primary)` — token CSS     |
| `recharts` | declarative React elements   | SVG    | `var(--primary)` — token CSS     |
| `chartjs`  | canvas + plugin registration | canvas | resolved with `getComputedStyle` |

The dataset is generated by a seeded LCG, so all three draw identical numbers and the demo can be
reloaded without changing what you compare.

The two library renderers are `lazy()`: selecting one downloads its chunk, which is also why each
lives at its own entry point (`@frontend-lab/charts/recharts`, `@frontend-lab/charts/chartjs`).
`pnpm bundle:report` reports those chunks separately, so the load cost is attributable rather than
hidden inside a demo chunk.

## The fund-flow diagram

The fourth card is a Sankey, and it is deliberately not part of the renderer switch: a branching flow
is a different chart type, not another implementation of the same line. None of the three renderers
above ships one — Recharts has no Sankey, Chart.js needs a community plugin, and `d3-sankey` is a
layout library rather than a renderer — so this one is hand-written in `packages/charts`:

- `sankey-layout.ts` is the pure part: node values (`max(in, out)`), one vertical scale shared across
  stages, node bands, ribbon anchor slices and the path strings. Nine `node:test` cases assert the
  geometry, because a mis-anchored ribbon still looks like "a diagram".
- `sankey.tsx` is the thin renderer: `<path>` per link, `<rect>` + label per node, colours from the
  `--chart-*` tokens.

The data is three stages — income, buckets, funds — so the diagram branches twice. One split would
not need a Sankey; a table would do.

## Chart colours are tokens now

`--chart-1..5` live in `tokens.css` (light and dark) and are mirrored in the `default` preset, so
`--chart-1` resolves differently per mode and the whole diagram repaints on a theme switch without a
re-render. That is the same rule as every other surface in the lab, applied to a chart: components
never pick hex values.

## What each cost buys

- **Hand-written SVG** is ~1 kB of code and draws exactly one chart type. Axes, ticks, tooltips,
  legends, brushing, resize handling and date scales are all still to write.
- **Recharts** brings scales, ticks, tooltips and responsive containers as React components. It
  renders SVG, so the token layer applies for free — including a theme switch with no re-render.
- **Chart.js** renders to canvas: cheaper for large datasets and heavier to integrate (manual
  registration, real colour values, and a theme switch does _not_ repaint the chart until something
  re-renders it).

The recorded numbers live in the page `scenarios/dashboard-builder`; the render figures in the demo
are measured live (`first render → committed DOM`), and the load figures come from
`pnpm bundle:report`.

## Pitfalls

- **Dynamic Tailwind classes do not exist.** `col-span-${span}` produces no CSS; the demo maps each
  span to a static class name, which is the only version Tailwind's scanner can see.
- **Recharts needs a sized parent.** `ResponsiveContainer` with no height renders nothing; the card
  gives it `h-24`.
- **Chart.js registration is easy to forget.** Without `CategoryScale`/`LinearScale` the chart
  renders axes-less and silently looks broken.
- **A canvas chart cannot use tokens directly.** `getComputedStyle` resolves `--primary` to a
  concrete colour at render time, so a theme switch needs a re-render to repaint — an SVG chart does
  not.
- **Layout animation and drag conflict.** `layout` on the sortable card would animate the same
  `transform` dnd-kit writes; `layout={!editing}` is the whole fix.
