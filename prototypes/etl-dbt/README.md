# etl-dbt

Local ETL demo with **dbt-core + DuckDB**: mock e-commerce raw data → staging
cleaning → marts (dimensions / facts / daily rollup), including an
**incremental model** end to end.

- Fully local: no database server, no cloud — DuckDB files only.
- `data/raw.duckdb` acts as the "source DB" (generated by a script), attached
  into dbt as the `raw` catalog; dbt writes results to `data/analytics.duckdb`.
- Created 2026-08-26 · status `experimental`

## Prerequisites

- [uv](https://docs.astral.sh/uv/)

## Setup

```bash
cd prototypes/etl-dbt
uv sync                       # installs dbt-core + dbt-duckdb into .venv
```

## Pipeline overview

```
scripts/generate_mock_data.py ──► data/raw.duckdb (source DB; raw catalog, main schema)
                                        │   attached as catalog "raw"
                                        ▼
                               dbt build (profiles/profiles.yml → DuckDB)
                                        │
              staging (views)           │   marts (tables)
        stg_customers / stg_products /  ├── fct_orders        (order fact)
        stg_orders / stg_order_items    ├── dim_customers     (customer + lifetime GMV)
                                        ├── dim_products      (product + units sold)
                                        └── daily_sales       (INCREMENTAL daily rollup)
                                        │
                                        ▼
                               data/analytics.duckdb (target DB, main schema)
```

## Usage

```bash
# 1. Generate mock raw data (default: 30 days from 2026-06-01, seed 42)
uv run python scripts/generate_mock_data.py

# 2. Full build: staging views + marts tables + daily_sales (first build is full)
DBT_PROFILES_DIR=profiles uv run dbt build

# 3. Inspect target data
uv run python -c "import duckdb; c=duckdb.connect('data/analytics.duckdb'); \
print(c.execute('select count(*) from daily_sales').fetchone()); \
print(c.execute('select * from dim_products order by units_sold desc limit 3').fetchall())"
```

### Incremental demo (the point of this prototype)

`daily_sales` is an incremental model: `materialized='incremental'` +
`incremental_strategy='delete+insert'` + `unique_key='order_date'`.

```bash
# append 2 new days (2026-07-01 ~ 2026-07-02) to the source DB
uv run python scripts/generate_mock_data.py --append-days 2

# rebuild ONLY daily_sales — dbt compiles the is_incremental() filter:
#   where order_date > (select max(order_date) from daily_sales)
DBT_PROFILES_DIR=profiles uv run dbt build --select daily_sales
# before: 30 rows (Jun 1–30)  →  after: 32 rows (adds Jul 1–2)
```

Why `delete+insert` instead of plain `append`:

- **Append** is fastest but cannot handle re-runs / corrected historical data
  (it blindly inserts duplicates).
- **delete+insert** first deletes rows whose `unique_key` (here `order_date`)
  appears in the new batch, then inserts — re-running a day is idempotent, so
  late corrections and backfills land correctly.
- On DuckDB this is the recommended strategy (no dedicated `merge` syntax
  needed; `merge` also works if you set `incremental_strategy='merge'`).

Incremental config lives both in `dbt_project.yml`
(`models.etl_dbt.marts.daily_sales`) and inline in the model header.

## Notes / gotchas

- **DuckDB 1.5 catalog naming**: for a local file `raw.duckdb` the *catalog*
  is the file name (`raw`), not `main`; the default *schema* stays `main`.
  Fully qualify as `raw.main.<table>` — bare `raw.<table>` is ambiguous.
  dbt sources use `database: raw, schema: main` (attach alias `raw`).
- Staging models are views; marts are tables. Bump `+materialized` in
  `dbt_project.yml` to change per-model.
- Source data stays immutable-ish: `generate_mock_data.py` rebuilds or appends
  by date; treat it as a stand-in for a real upstream OLTP/CDC source.
- Use a fixed `--seed` for reproducible mock data.
